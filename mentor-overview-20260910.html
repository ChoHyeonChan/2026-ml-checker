멘토링 자료 — MABC 2026 결선 MVP 개요

예선 당선 스킬: ml-data-leakage-checker  |  플랫폼: Timely(확정)  |  목표: 수상 목표 / 연구자 대상 서비스 MVP
한 줄 설명
ML 전처리 코드를 넣으면 데이터 누수(data leakage) 패턴을 자동으로 검사해 주는 서비스입니다. 결과는 확정위반 / 의심 / 이상없음 3분류 + 줄 번호 + 수정 방향만 짧고 간결하게 제공합니다.

1. 왜 이 서비스를 만들려고 하나 (문제 정의)

  • 전처리 코드 검토할 때마다 데이터 누수를 사람이 직접 찾는 반복 작업이 생김
  • 타겟 인코딩, 피처 추가, 스케일링, CV 분할, 시계열 순서 변경 등에서 재확인이 길어짐
  • 실행은 되고 점수도 좋지만, 누수가 숨어 늦게 발견되면 튜닝·모델 비교를 처음부터 다시 해야 함
  • 코드가 길어질수록 누수 지점을 한 번에 파악하기 어려움
즉, “코드는 돌아가는데 누수가 숨어 있어서 나중에 다시 다 해야 하는 문제”를 줄이려는 목적입니다.

2. 이 서비스가 해결하려는 것 (가치/Solve)

가치 문장 후보
“전처리 코드를 넣으면 데이터 누수 의심 지점을 확정위반/의심/이상없음 3분류 + 줄 번호 + 수정 방향으로 빠르게 확인할 수 있어, 모델 학습 전 코드 검토 시간을 줄여준다.”
과정 설명은 생략하고 결과만 간결하게 주는 것이 우리 스킬의 특징입니다. 원본 코드는 수정하지 않고 지적만 제공합니다.

3. 핵심 사용자 (Who)

  • 1차 타겟: ML 전처리/학습 파이프라인을 직접 작성·수정하는 연구자
    • 학부연구생, 대학원생, 주니어 연구원, 작은 랩/팀 실무자 등
  • 확장 타겟: 교수, 시니어 연구원, 데이터 분석하는 연구자도 “코드 리뷰/점검 대행” 느낌으로 사용 가능
MVP에서는 1차 타겟을 중심으로 화면·문구·시나리오를 잡고, 확장 타겟은 P1 또는 발표/데모에서 보여주는 방향으로 생각 중입니다.

4. 언제 쓰는가 (When)

  • 모델 학습 전, 전처리 파이프라인/코드 검토하고 나서
  • 전처리 코드 수정·리팩토링할 때
  • 팀 코드 리뷰할 때 데이터 누수 의심 지점을 빠르게 공유하고 싶을 때
  • CV/타겟 인코딩/스케일링/피처 추가 등 넣고 나서 “이게 누수인지” 다시 확인할 때
  • 결과는 좋은데 뭔가 찝찝할 때, 코드부터 점검하고 싶을 때

5. 입력과 출력 (Input & Output)

입력

  • 전처리 코드 (문자열 붙여넣기 / 파일 업로드 등)
  • 가능하면 다중 파일, 표준입력, 코드 문자열 입력도 지원하려는 방향

출력

  • 3분류: 확정위반 / 의심 / 이상없음
  • 확정위반: 이유 한 줄 + 줄 번호 + 수정 방향
  • 의심: 의심 지점 + 줄 번호 + 수정 방향
  • 이상없음: 짧게 pass
  • 예외/판정불가: 빈 입력, 비파이썬, ML 전처리 코드 아님, split 경계 없음 등 사유 안내
MVP에서는 입력은 코드 문자열(붙여넣기) 우선으로 시작하고, 파일 업로드/다중 파일 등은 P1에서 확장하는 쪽으로 검토 중입니다.

6. 기반 개념 (팀이 얘기 중인 개념 정리)

머신러닝에서 데이터를 왜 나누는가

  • 학습 데이터(Train): 모델이 공부할 자료
  • 검증 데이터(Validation): 중간중간 “지금 설정 괜찮은지” 확인하는 자료 — 대화에서는 모의고사로 비유
  • 테스트/평가 데이터(Test): 진짜 마지막 시험. 개발 과정에서는 최대한 보지 않고, 마지막에 평가용으로만 쓰는 게 원칙

데이터 누수(Data Leakage)란

  • 원래 학습 데이터만 보고 배워야 하는데, 평가(테스트) 데이터 정보까지 미리 봐버린 상황
  • 그러면 모델이 그 평가 데이터를 “외워버린” 것처럼 돼서, 평가할 때 성적이 부풀려질 수 있음
  • 예시:
    • 테스트 데이터를 학습 데이터에 섞는 경우
    • 테스트 데이터 정답을 보고 모델/규칙을 수정하는 경우
    • 전체 데이터에 대해 정규화·전처리한 뒤 분할하는 경우
    • 미래 시점 정보를 이용해 과거를 예측하는 경우
    • 중복 데이터가 학습/테스트 양쪽에 들어가는 경우

과적합(Overfitting)과의 차이

  • 과적합: 모델이 학습 데이터의 특징/노이즈까지 너무 외워서 새로운 데이터에 약해지는 현상
  • 데이터 누수: 평가 데이터의 정보가 학습/모델 선택 과정에 섞여 들어가는 문제
  • 둘은 관련 있지만 같지는 않음. 평가 데이터를 학습에 사용하면 해당 데이터에서는 성능이 높아 보일 수 있지만, 새로운 데이터에선 기대와 다를 수 있음
정리: 이미지 속 대화의 핵심은 “학습/검증/테스트를 왜 나누는지, 평가 데이터를 미리 쓰면 왜 문제인지, 그리고 그걸 막으려고 우리 스킬을 만든 것”입니다.

7. 우리 스킬이 저 개념에서 뭘 체크해주나

  • 전체 데이터 기준으로 fit을 먼저 해버리는 패턴 → 분할 전에 스케일/인코딩 등을 전체에 적용하면 누수 의심
  • 타겟(정답)을 직접 사용해버리는 패턴 → 정답 정보가 전처리/학습 과정에 새는 것 점검
  • 시계열 순서 변경/셔플 관련 패턴 → 시간 순서가 중요한 데이터에서 순서 망가지면 누수/왜곡 가능성 점검
  • split 경계와 fit 호출 위치/순서 비교 → “나누고 나서 fit해야 하는데, 나누기 전에 fit했네” 같은 순서를 잡아줌
  • 사용자 정의 함수 안 fit, 객체 전달/재할당 추적 → 코드가 함수/객체 타고 돌아다니면서 누수 요인이 숨는 경우 점검
  • 파이프라인 정상 사용 시 오탐 완화 → 진짜 문제 아닌 걸 무조건 욕하지 않게 조정
  • 노트북 셀 순서 한계 안내 → 실제 문제와 셀 순서만 보면 애매할 수 있음을 안내
즉, “데이터를 잘못 쓰면 문제”라는 아이디어를 전처리/학습 코드에서 패턴으로 먼저 잡아주는 도구로 만든 것입니다.

8. MVP 범위 방향 (P0 / P1)

P0 (필수 — 제출 직전까지 돌아가야 하는 것)

  • 코드 입력(문자열/붙여넣기 기준) → 3분류+줄번호+수정방향
  • 확정위반 시 이유 한 줄 포함
  • 예외 처리: 빈 입력/비파이썬/ML 전처리 코드 아님/split 없음 → 판정 불가 또는 사유 안내
  • 기본 결과 화면 + 첫 방문자 이해 가능한 안내
  • 백엔드: 예선 스킬 중심 동작 + 안정적 호출/확장
  • 배포/공개 URL, 시크릿 창 테스트, 심사 종료까지 유지
  • 제출물: 발표자료 PDF(5장 이내·Noto Sans), 포스터(A1), 데모 영상(MP4 3분 이내), PRD(2쪽 내외)

P1 (시간 남으면 붙이기)

  • 파일 업로드/stdin/다중 파일 지원
  • 결과 복사/공유/저장/이력 등 편의 기능
  • 예시 코드/온보딩/가이드 강화
  • 교수/시니어 코드 리뷰 공유 시나리오 확장
  • 데모 영상 퀄리티, 발표 스토리라인 다듬기

10. 오늘 멘토링에서 여쭤보고 싶은 포인트 (요약)

  1. 연구자 타겟으로 좁힐 때 1차 범위를 어느 정도로 잡으면 좋을까요? (학부연구생/대학원생/주니어 연구원 중심 vs 교수/시니어 포함)
  2. 사용 시점 중 “모델 학습 전 점검”과 “팀 코드 리뷰 공유” 중 MVP 메인 맥락을 어디로 잡는 게 더 설득력 있을까요?
  3. 입력은 코드 붙여넣기만으로 충분할까요? 파일 업로드/stdin/다중 파일까지 P0로 봐야 할까요?
  4. 결과 화면은 얼마나 친절해야 첫 방문자도 이해할까요? 체크리스트형 결과 특징을 살리면서도 사용성(15점)을 잡으려면 균형이 어디에 있을까요?
  5. Solve 한 문장/가치 메시지를 어디에, 어떤 톤으로 강조하는 게 좋을까요?
  6. 예선 스킬을 서비스에서 “그대로 호출”하면서 수정·확장 범위를 어디까지 하는 게 안전할까요? “중심 역할 + 안정 동작” 기준을 어떻게 보면 좋을까요?
  7. P0/P1 우선순위에서 지금 시점에 반드시 잡아야 할 것과 미뤄도 되는 걸 어떻게 나누면 좋을까요?
  8. 발표자료 5장 이내/데모 영상 3분 이내에 기획 메시지를 담을 때, “문제 → 해결 방식 → 예선 스킬 활용” 흐름을 어떤 순서로 보여주면 좋을까요?
