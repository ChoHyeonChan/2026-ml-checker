> 예선 당선 스킬: `ml-data-leakage-checker`
> 대회: Making AI Beneficial Challenge (MABC) 2026 결선

> 현장 발표: **9월 19일(토) 11:00~17:00** @ 한국과학기술회관 B1 대회의실1 (팀원 1인 이상 필수 참석)
> 목표: **1등** — 평가지표 배점·규정·제출물을 기준으로, 우리 서비스가 가장 설득력 있게 동작하게 만들기

## 1. 이 지침서의 목적

이 문서는 예선 통과팀에서 **본선 MVP를 만들고 제출하기까지** 팀원이 함께 보고 실행할 수 있게 정리한 지침서예요. 단순 안내가 아니라, **무엇을 언제 어떻게 점검하고, 무엇을 만들지**까지 담고 있어요.

- **왜 만드는지**: 예선 `ml-data-leakage-checker`를 "나만 쓰는 스킬"에서 "누구나 쓸 수 있는 서비스 MVP"로 확장해서, 규칙에 맞게 제출하고 현장 발표까지 완주하는 게 목표예요.
- **무엇을 담았는지**: 결선 개요·일정·플랫폼·크레딧·규정·평가지표, 서비스 MVP 기획 프레임(MVP 5 체크포인트), 제출물 5종 명세, 코드/보안/폴더 구조/개발 체크 운영 원칙, 제출 전 체크리스트, 실행형 점검 도구.
- **어떻게 쓸지**: 먼저 1~3장으로 큰 그림을 잡고, 4장으로 서비스 기획을 잡고, 5장으로 코드/보안/폴더/개발 운영 원칙을 잡고, 6장으로 뭘 제출해야 하는지 확인하고, 7장 체크리스트로 마감 직전 점검을 해요.

## 4. 서비스 MVP 기획 — "스킬 → 서비스" 전환 프레임

### 4-1. 스킬 vs 서비스
- **스킬**: '나'만을 위한 고려 (개인적 고민·생각 담긴 결과물)
- **서비스**: '불특정한 다수'를 고민 (다른 사람 상황·환경 넓게 고려)

### 4-2. MVP 5가지 체크포인트 (서비스 기획의 뼈대)
서비스 만들기 전에 다음 5가지 질문에 답해봐요. 이게 기획력(25점)·창의성(20점)·기술 구현도(15점)의 기초가 돼요.

1. **Who (사용자 정의)**: 구체적으로 어떤 문제를 겪는 사람인지
   - "모든 사람" 말고, 구체적인 마이크로 타겟으로
   - 우리 팀 예: 데이터 리키지에 관심 있는 ML 실무자/분석가/학생 등 — 누구를 겨냥할지 구체화
2. **When (사용 시점 명시)**: 언제 이 서비스를 찾고 쓰는지
   - 우리 팀 예: 모델 학습 전/후 데이터 품질 점검할 때, 전처리 파이프라인 점검할 때 등
3. **Input & Output (입출력 형식)**: 사용자 입력 형태, 서비스 출력물
   - 우리 팀 예: (입력) 데이터/전처리 코드/파이프라인 정보 등 / (출력) 리키지 의심 지점, 판단 근거, 조치 제안 등
4. **Setup (설정값)**: API 키, 외부 서비스 연동(MCP), 환경 변수 등 서비스 구동 필요 설정값
   - **대부분 외부 노출되면 곤란 → 따로 등록·관리** (Vercel 환경 변수 등)
5. **Solve (가치 정의)**: 최종적으로 어떤 문제 해결하고 어떤 가치 주는지 **한 문장 정리**
   - 우리 팀 예: "`ml-data-leakage-checker`를 누구나 써서, 모델 개발 과정에서 데이터 리키지 위험을 쉽게 점검하고 조치 방향을 얻을 수 있는 서비스" 같은 식으로 한 문장 정리

### 4-3. MVP 정의·범위
- **MVP**: 최소한의 기능만 포함, 사용자가 겪던 문제를 실제로 해소해줘야 함
- 범위 모호해지면 불필요 기능 추가돼 서비스 정체성 잃음 → 5가지 체크포인트로 범위 명확히
- **기능 범위**: P0(필수 기능) / P1(있으면 좋은 기능)로 구분해서 잡기

### 4-4. PRD (Product Requirement Document)
- 무엇을 만들지, 어디까지 만들지, 어떻게 만들지 적은 문서
- 구성 요소: 누가 쓰고, 왜 쓰고, 입출력은 뭔지, 핵심 기능(P0/P1), 설정 조건, 완료 조건 등 구체적으로 명시
- AI에게 구체적으로 요청해 PRD 초안 생성 가능 (Skill-to-Service 미니 PRD)
- **AI 생성 PRD 반드시 읽고, 내 MVP 가치·기능 목록과 일치하는지 대조** — AI 믿고 그대로 두면 안 됨
- 제출용 PRD: **PDF 또는 Markdown (2쪽 내외)**, Skill-to-Service 미니 PRD

### 4-5. 배포 (Deployment)
- 내 컴퓨터에서만 동작하던 서비스를 다른 사람이 쓸 수 있도록 인터넷 공개
- **Vercel 무료 버전** 활용하면 코드 없이 손쉽게 배포 가능 (교육에서 활용)
- 환경 변수 설정: API 키 등 민감 설정값은 Vercel에서 환경 변수로 등록·관리
- **배포 보호 해제**: Vercel 프로젝트 설정에서 Deployment Protection Off → 로그인 없이 누구나 접근 가능하게 (공개 URL 요건 관련)
- 배포 후 MVP가 잘 작동하는지, 설정한 가치 잘 만들어내는지 테스트
- 문제 발생 시: "무엇을 했고, 무엇을 기대했고, 실제로는 어떻게 나왔다" 형태로 AI에게 피드백 제공 → 수정 요청
- GitHub-Vercel 연동 시 코드 변경 시 Vercel 자동 배포 가능, 코드 보관·관리 측면

## 5. 코드·운영 원칙 (우리 팀 개발 수칙)

지침서 본론 중 가장 실무적인 부분이에요. 아래 원칙은 **대회 규정 준수 + 개인정보/키 유출 방지 + 에러 리체크 + 추후 수정 용이성**을 한 번에 잡기 위한 거예요.

### 5-1. 코드는 길지 않고 읽기 편하게, 주석 달기
- 기능 단위로 **적당히 짧게** 나누고, 한 파일/함수가 너무 길어지지 않게 유지
- 핵심 로직·입출력·가정·주의점은 **주석으로 짧게** 남겨서 팀원이 나중에 봐도 이해되게
- 주석은 "무엇을 하는지"보다 **"왜 이렇게 했는지"** 중심으로 남기면 좋음 (특히 예선 스킬 호출/확장 부분)
- 너무 장황한 주석보다, 읽는 사람이 막히는 지점 위주로 달아두기

### 5-2. 기능별 폴더 구조 (추후 확장 용이하게)
지금은 MVP 범위를 작게 시작하더라도, **나중에 기능 추가/수정할 때 편하도록** 폴더 구조는 미리 잡아두는 게 좋아요.

예시 구조 (서비스 성격에 맞춰 조정):
```
mabc-service/
├── README.md            # 서비스 개요, 실행 방법, 환경변수 안내
├── prd/                 # PRD 초안/최종본 (PDF 또는 Markdown)
├── poster/             # 포스터 원고/최종 PDF
├── presentation/       # 발표자료 원본/최종 PDF
├── demo/               # 데모 영상(MP4), 캡처 등
├── src/                # 서비스 핵심 코드
│   ├── main.py         # 진입점
│   ├── api/            # API/라우팅 등 (필요 시)
│   ├── checker/        # ml-data-leakage-checker 관련 로직 (예선 스킬 활용 중심)
│   └── utils/          # 보조 함수
├── config/             # 설정 관련 (환경변수 읽는 코드 등, 실제 키는 넣으면 안 됨)
├── tests/              # 간단한 동작 확인용 테스트/체크 스크립트
├── .env.example        # 필요한 환경변수 목록 예시 (실제 값 X)
├── .gitignore          # 키/환경변수/캐시/빌드 산출물 제외
└── requirements.txt / pyproject.toml 등 의존성 명시
```

- 폴더/파일 이름은 **무엇이 들어있는지 바로 알 수 있게** 짓기
- 예선 스킬 호출/확장 부분은 `checker/`처럼 구분하면, 나중에 "어디가 예선 스킬 중심인지" 한눈에 보기 좋음
- 제출 전 `src/`, `config/`, `tests/` 등 실제 동작에 필요한 것만 깔끔하게 정리

### 5-3. 개인정보·키·토큰 유출 방지 (가장 중요)
공개 저장소(Public)로 내기 때문에, **한 번 올리면 되돌리기 어려움**을 전제로 철저히 챙겨야 해요.

- **소스 코드**: API 키, 토큰, 비밀번호, 개인 계정 정보, 내부 URL을 코드에 하드코딩하지 않기
- **환경 변수/설정**: 실제 키는 코드 밖에서 관리 (로컬에서는 .env, 배포에서는 Vercel 환경 변수 등). `.env.example`에는 키 이름만 적고 값은 넣지 않기
- **.gitignore**: `.env`, `*.env`, 키 파일, 인증서, 빌드 산출물, 캐시 등 제외 확실히 하기
- **커밋 이력**: 실수로 키가 들어간 커밋이 있으면 단순히 삭제만으론 부족할 수 있음 → 이력 확인/정리 필요. 공개 전 **전체 커밋 로그**를 한번 훑기
- **PRD·서비스 UI**: 설명 문구나 화면 캡처/예시에도 실제 키가 보이지 않게 하기
- **데모 영상**: 녹화 화면에 키/토큰/개인 정보가 보이지 않는지 확인
- **제출 전 최종 확인**: 저장소를 공개(Public)로 바꾸기 전에 한 번 더 전체 코드에서 민감 정보 탐색

### 5-4. 대회 규정 준수 (개발 중 상시 체크)
- LLM은 Solar Pro 4만 사용, 허용된 개발 도구(Timely·Hermes)만 사용
- 예선 당선 스킬(`ml-data-leakage-checker`)을 서비스 핵심 로직에 필수 포함 (그대로 호출 원칙, 서비스화 위한 수정·확장 허용)
- 타인 스킬/아이디어/에이전트 무단 사용 금지
- 배포는 독립 공개 URL (로컬 X, 타임리 내 동작 X, 타임리 워크스페이스 공유 링크 X)
- 제출 이후 배포 코드 수정 불가 → 제출 직전 최종본으로 확정

### 5-5. 중간중간 코드 오류/에러 리체크
MVP를 만들다 보면 100% 한 번에 완성되기보다, 만들면서 계속 확인하는 게 안전해요. 아래 사이클을 개발 중간에 넣어두면 에러/오류를 미리 줄일 수 있어요.

1. **작은 단위로 만들고 바로 확인**
   - 기능 하나 추가할 때마다 로컬/개발 환경에서 동작 확인
   - "입력을 넣었을 때 의도한 출력이 나오는지" minimal case로 먼저 확인
2. **에러 발생 시 기록 방식**
   - "무엇을 했고, 무엇을 기대했고, 실제로는 어떻게 나왔다" 형태로 남기면 원인 찾기 쉬움
   - 오류 메시지, 재현 방법, 시도한 조치 정도가 있으면 다음 수정/문의 때 도움됨
3. **핵심 경로 우선 점검**
   - 서비스의 핵심 기능(예선 스킬 호출/확장 포함)이 가장 먼저/stable하게 동작해야 함
   - 부가 기능(P1)보다 핵심 기능(P0) 안정화를 먼저
4. **배포 전 통합 확인**
   - 로컬에서만 되고 배포본에서 깨지는 경우가 흔함 → 배포본 기준으로 동작 테스트
   - 시크릿 창/다른 환경에서도 접속·실행 되는지 확인
5. **제출 전 최종 리체크**
   - 코드 전체 푸시, Public 설정, 민감 정보 없음, 배포본 식별 정보(커밋 해시 등) 확보
   - 데모 영상·발표자료·포스터도 각각 규정 형식으로 최종 확인
